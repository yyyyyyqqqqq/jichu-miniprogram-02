# Final Release Step 3C-2 staging 双账号验收单

本验收单只用于 staging。禁止在 production 执行、造数或切换学校。

## 前置状态

- 开发者工具明确显示 staging。
- 买家 A、卖家 B 均为真实登录账号，资料完整。
- A、B 的初始当前学校均为学校 A，且学校为 active + valid。
- B 当前允许换校，并准备在验收中仅切换一次：学校 A → 学校 B。
- B 在学校 A 发布至少两个仍可识别的测试商品：
  - H：用于建立历史预约和历史会话。
  - N：保持 available，用于 B 换校后的新预约/新会话边界测试。
- 不要复用已 reserved、sold、offline 或已有进行中预约的商品验证“新预约”。

如果卖家 B 当前已经在学校 B，不要先切回 A 再立即切回 B；7 天换校冷却会污染验收。应换用满足前置状态的 staging 账号，或另行执行经过确认的 staging-only 测试状态准备。

## 执行顺序

### 1. 用户主页学校展示

1. A 打开 B 的用户主页。
2. 确认顶部显示学校 A 的真实名称。
3. 确认没有显示“校园信息待完善”。

记录：`PASS / FAIL`。

### 2. 同校新预约与历史基线

1. A 打开商品 H 的聊天页并发一条测试消息。
2. A 对 H 发起新预约。
3. 确认提示“预约已发起”，详情可由 A、B 打开。
4. B 接受预约，确认状态进入“已接受”。
5. A、B 均确认旧会话和消息可读。

记录：同校预约 `PASS / FAIL`；历史预约基线 `PASS / FAIL`；历史聊天基线 `PASS / FAIL`。

### 3. 卖家换校

1. B 从学校 A 切换到学校 B。
2. 确认 B 当前主页/市场已进入学校 B。
3. 不编辑商品 H、N 的原始发布学校。

记录：`PASS / FAIL`。

### 4. 跨校新预约

1. A 仍保持学校 A。
2. A 通过历史入口或可控测试入口打开旧商品 N。
3. A 尝试发起新的预约。
4. 必须被拒绝。
5. 友好提示应为“卖家已更换学校，该商品暂不支持发起新的面交预约”或页面等价提示。

记录：拒绝 `PASS / FAIL`；提示友好 `PASS / FAIL`。

### 5. 历史预约

1. A、B 分别重新打开商品 H 的既有预约详情。
2. 确认详情仍可读，且显示换校/跨校关系但不丢失历史。
3. 按当前状态机执行一个合法后续动作：取消或完成。
4. 确认合法动作成功；不要用非法状态动作代替此项。

记录：详情可读 `PASS / FAIL`；状态机动作 `PASS / FAIL`。

### 6. 历史聊天

1. A、B 分别打开 H 的旧会话。
2. 确认换校前消息仍完整可读。
3. 确认历史会话没有因 B 换校消失。

记录：`PASS / FAIL`。

### 7. 新会话边界

1. B 已在学校 B，A 仍在学校 A。
2. A 使用旧商品 N 尝试新建会话，或在已有 pair conversation 中建立/刷新 N 的交易上下文。
3. 系统必须拒绝新的 stale product context，不能因复用 pair conversation 绕过 current-school boundary。
4. 旧会话和旧消息仍须可读。

记录：新上下文拒绝 `PASS / FAIL`；旧历史保留 `PASS / FAIL`。

## 最终记录

- 用户主页真实学校名：`PASS / FAIL`
- 同校新预约：`PASS / FAIL`
- 跨校新预约拒绝：`PASS / FAIL`
- 历史预约可读及合法流转：`PASS / FAIL`
- 历史聊天可读：`PASS / FAIL`
- 新会话边界：`PASS / FAIL`
- 控制台异常：`0 / 非 0`
- staging blocker：`无 / 说明`

只有以上全部 PASS、控制台异常为 0，且自动回归继续通过时，才能给出：

`READY FOR PRODUCTION DEPLOY AUTHORIZATION`
